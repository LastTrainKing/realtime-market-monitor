# 数据源故障诊断报告：「无法连接数据源」

> ## ⚠️ 重要更正（2026-09-25 16:52 复测后）
>
> **本报告最初把根因写成"东方财富下线了 `fflow/kline` 接口"，这个结论是错的。**
>
> 16:52 复测同一批接口，结果**完全反过来**：
>
> | 接口 | 15:5x | 16:52 |
> | --- | --- | --- |
> | `stock/fflow/kline/get` | ❌ 断开 | ✅ **HTTP 200（连测 6 次全成功）** |
> | `clist/get` | ✅ HTTP 200 | ❌ 断开 |
> | `ulist.np` / `trends2` / `fflow/daykline` | ✅ | ✅ |
>
> 所以真实情况是：**这些接口会间歇性断连**（服务器 TLS 握手后直接断开、
> 不发 HTTP 响应），而且**不同接口在不同时间点被挡**。
>
> ### 修正后的根因
>
> **不是接口下线，是服务端对这个 IP 的间歇性拒绝（疑似反爬/限流）。**
> 佐证：本应用原来每轮刷新要发 **1000 个请求**（每板块一次 `fflow/kline`），
> 30 秒一轮 —— 这种访问模式极可能触发临时限流，而限流是按接口/边缘节点
> 轮换生效的，所以看起来像"某个接口挂了"。
>
> ### 结论对修复方案的影响
>
> **方案方向不变，而且更有理由了**：
>
> * 请求数从 **1000/轮 降到约 10/轮**（两个数量级）→ 大幅降低触发限流的概率；
> * 错误分类细分（DNS/TCP/TLS/无响应）保留 —— 这次就是靠它才能一眼看出
>   "连上了但对方没回"，而不是笼统的"无法连接"；
> * 重试/退避/熔断本来就该处理这种**瞬时**失败（见第四节）。
>
> 下面正文保留原始记录，但**第一节的"接口被下线"请按本节更正理解**。

## 一、结论（一句话）

**网络完全正常。是东方财富把「分钟资金流」接口 `stock/fflow/kline/get` 下线了** ——
服务器在 TLS 握手成功后**直接断开、不返回任何 HTTP 响应**。

应用把这一类失败归成了 `NETWORK_UNREACHABLE`，界面显示"无法连接数据源"，
于是所有人都在查网络 —— **而网络没有问题**。

## 三、"无法连接数据源"是谁产生的

```
reqwest 报错（连接被对端断开）
   ↓
errors::classify_reqwest()
   ↓  err.is_connect() == true
AppError::network_unreachable()      ← errors/mod.rs
   ↓  code = "NETWORK_UNREACHABLE", message = "无法连接数据源"
前端 errors.ts::HINTS["NETWORK_UNREACHABLE"]
   ↓
界面：「无法连接数据源」
```

**根因是分类器太粗**：reqwest 的 `is_connect()` 同时覆盖
**DNS 失败 / TCP 被拒 / TLS 握手失败 / 连上了但对方没回内容** ——
四种完全不同的病因压成同一句话，所以查不到。

### 已修复

`classify_reqwest` 现在按错误特征细分出可定位的 code：

| 新 code | 含义 |
| --- | --- |
| `NETWORK_DNS_ERROR` | 域名解析失败 |
| `NETWORK_TCP_ERROR` | TCP 建连失败 |
| `NETWORK_TLS_ERROR` | TLS 握手失败 |
| `NETWORK_EMPTY_RESPONSE` | **连上了但对方没返回内容**（本次事故） |
| `NETWORK_FORBIDDEN` | 403 明确拒绝 |
| `NETWORK_RATE_LIMITED` | 429 限流 |
| `NETWORK_UNKNOWN_ERROR` | 判不出类别时**保留原文**，不吞细节 |

前端同步加了各自的文案。以后同类问题一眼能看出该查哪一层。

## 四、熔断器审计（用户重点关注）

**结论：熔断器本身是好的，不是它卡死。**

证据（应用日志）：

```
15:45:13  连续失败达到阈值，熔断器打开 failures=5..9
15:46:20  熔断器恢复：OPEN/HALF_OPEN → CLOSED
15:46:20  日历已联网更新（可信） days=90      ← 探测成功，自动恢复
```

* `breaker.rs` 有完整的 `CLOSED → OPEN → HALF_OPEN → CLOSED` 状态机，
  冷却结束后放行探测，探测成功即恢复；
* 状态是**进程内**的（`epoch: Instant::now()`），重启即清零，不会跨进程卡死；
* 单测覆盖了开/半开/恢复/半开失败重开四种路径。

所以"熔断一直 OPEN 导致网络恢复也不请求"这个担心**在本项目不成立**。
真正的问题是**它保护的接口本身已经死了**，恢复探测必然失败。

## 八、已实施的替代方案（方案 A）

**没有停在"建议"** —— 已经落地。

### 核心思路：累计快照相减

`clist` 的 `f62` 是**当日累计**主力净额，接口可用。于是：

```text
每轮采样一次「当日累计」        →  cum(T1), cum(T2), cum(T3) ...
相邻两次相减                   →  interval(T2) = cum(T2) - cum(T1)
```

得到的 `interval` 就是**该时段的区间净流入** ——
与面板原来的口径**完全一致**。所以面板的数据模型、缓存、快照构建器、
开盘检测、区间累计**全都不用改**。

这比"把口径改成累计"好得多：**没有模糊区间/累计的区分**，
历史数据与新数据可以直接拼在同一条曲线上。

### 请求量：降了两个数量级

| | 请求数 |
| --- | --- |
| 旧（每板块一次 `fflow/kline`） | **1000 次 / 轮** |
| 新（`clist` 分页扫一遍） | **约 10 次 / 轮**（1000 板块 ÷ 每页 100） |

按 60 秒采样、盘中 4 小时算：旧 ≈ 48 万次/天 → 新 ≈ **2400 次/天**。
这同时解决了之前一直担心的 IP 风控问题。

### 新增文件

`apps/backend/src/application/services/sector_flow.rs`

| 函数 | 职责 |
| --- | --- |
| `fetch_cumulative` | 分页扫 `clist`，拿全部板块的当日累计（约 10 个请求） |
| `diff_sweep` | 相邻两次相减 → 区间值；标出"当天第一次" |
| `write_into_panel` | 写进面板的当前分钟行（**亿元**，与历史一致） |
| `mark_source` | 来源标成 `clist-sample`，与 `live` 区分 |

改动：`panel.rs` 新增 `sample_panel`（替换原 `fetch_panel` 调用）、
`AppState` 加 `last_sweep`（存上一轮采样供相减）。

### 口径的诚实说明（写进代码注释）

* 每个区间的**时间标签 = 采样时刻**，不是"这一分钟"；
* **当天第一次**采样没有前值可比，只能把累计值当"开盘至今"并标出 `firstOfDay`；
* **中途新出现**的板块区间未知 → 记 **0**，
  **绝不**把它的当日累计当区间（那会凭空造出一笔巨额流入把榜单冲乱）；
* 数据带 `source = "clist-sample"`，与原来的 `live` 区分开。

### 9 条单测钉住的行为

`diff_of_two_cumulatives_is_the_interval` · `first_sweep_of_the_day_is_flagged` ·
`appearing_and_disappearing_sectors_are_handled` ·
`writes_intervals_into_the_right_cell_in_yi` · `unknown_minute_writes_nothing` ·
`sectors_not_in_panel_are_skipped` · `names_are_filled_without_overwriting` ·
`source_is_marked_so_two_origins_are_distinguishable` ·
**`sum_of_intervals_equals_last_cumulative`**（证明相减法无系统性偏差）

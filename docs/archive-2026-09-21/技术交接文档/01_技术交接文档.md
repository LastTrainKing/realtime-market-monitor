## 一、项目是什么

一套 **A 股盘中资金流向分析工具链**，围绕「板块/概念资金流 + 盘中辨识度」展开。
共五种交付形态，同一套分析内核（`salience.py`；单文件版与 APK 版为 JS 重写）驱动：

| 形态 | 位置 | 技术栈 | 说明 |
|---|---|---|---|
| **原生桌面版**（主力） | `%LOCALAPPDATA%\FlowLiveNative\` | PySide6 + matplotlib QtAgg | 9 个页签，无浏览器内核，onedir 打包 |
| 分析工具 | `outputs\flowtool\` | 纯标准库 + 相对路径自包含 | 命令行跑，出 HTML 报告 + PNG |
| 实时看板（浏览器） | `桌面\资金流向实时看板\` | `server.py` 标准库 + Canvas 单页 | 只监听 127.0.0.1:8848 |
| 单文件看板 | `桌面\资金流向实时看板\资金流向看板.html` | 单 HTML + JS | 离线可用，含同样的分析逻辑（JS 重写） |
| **Android APK** | `outputs\资金流向看板_Android\` | WebView 壳 + JDK/d8/jarsigner 手工构建 | Day2 交付；工程在 `work\apk_build\` |

**数据源**：东方财富 push2 公开接口（板块分时资金流 `klt=1`、指数分时 `trends2`）。
全市场约 1000 个板块，剔除统计桶与行业层级重复后约 400+ 概念题材 + 31 一级行业。

### v1.2.3 的两个关键认知（勿退化）
- **onefile 每次启动解包 69MB 到 `%TEMP%\_MEIxxxx`（实测 1.64s）**，
  这段发生在 Python 代码执行**之前**，任何代码优化都碰不到 → 只能换打包形态。
  A/B 实测：onefile 3.67s（最慢 4.88s）vs **onedir 1.84s（极稳）**。
  附带：onefile 被强杀会残留 `%TEMP%\_MEI*`，实测累积 30 个 / 3.8GB。
- **交易日历「磁盘优先」**：旧逻辑「先联网 → 失败才读盘」每次白等一次往返（894ms）；
  改为「今天写过的盘缓存 → 内存 → 联网」后降至 0.8ms。

### v1.2.4 的核心（勿退化）
**两套坐标系在同一根轴上打架**：
```python
画曲线（旧）   ax.plot(range(len(s)), s)      # x = 数组下标 0,1,2,…
标刻度（旧）   _minute_index(lab)             # x = 分钟序号 09:31=0 … 15:00=239
```
两者**只有面板一分钟都不缺时才重合**。而盘中面板必然有缺口（程序没开着的那几分钟永久缺失）
→ 41 个点被压缩到左边 17%，末端读作 10:11，**落后真实数据 66 分钟**。

修法三件套（缺一不可）：
1. `_x_positions()` —— 曲线改按分钟序号落位，内部吃三种脏数据（头部缺标签倒推 /
   不可解析标签前向 +1 续格 / 重复倒序强制严格递增）
2. `_row_at_x()` —— 悬停与准星改用同一套坐标（鼠标 x 是"第几格"，数据是"第几行"）
3. 数据侧堵源头 —— `clamp_to_bar()` + `spot_gap_minutes()` + `SPOT_MAX_GAP_MIN=6`

**顺带挖出的更深 bug**：`datetime.now().strftime("%H:%M")` 直接当行标签 →
午休期间每刷新一次塞一行假刻度 `11:43`（A 股 11:31~12:59 无数据）→
`_minute_index("11:43")` 返回 None 带偏整条轴。

## 三、本次任务（v1.2.5）完整记录

### 用户原话
> 「请修复「全天关键节点榜」中时间节点的排序问题：当前各时刻排列无序、杂乱，
> 需按时间先后顺序（例如从早到晚）对全天关键节点正确排列。请确保排序逻辑准确、
> 覆盖所有节点，并保证在数据更新或刷新后仍维持有序展示。」

### 根因：一个函数被两种用途共用，排序口径只服务了其中一种

`salience.timeline_summary()` 的结尾是：
```python
rows.sort(key=lambda r: -r["strength"])      # 按强度倒序
```

**它当初为什么这么排**：这个函数最早是给**收盘解说的文字稿**用的 ——
只取前几条念出来，谁最劲爆谁靠前，对"听"是对的。

**为什么现在必须改**：它后来被复用成**表格**的数据源（原生版页面 + HTML 报告）。
表格是**用来扫的**，时间跳跃的表格每一行都要重新定位，读者本能判定为"乱"。

**实测证据**（面板 20260918，79 个节点）：
```
旧口径：13:24 → 13:27 → 13:45 → 13:51 → 13:15 → 13:12 → 13:09 → 11:03 …
                    ↑ +18分          ↑ -36分          ↑ -126分（回跳）
相邻两行回跳 40 次 / 78 次比较，近一半在往回走
```

**为什么改成时间序不丢信息**：强度**不需要靠行序表达** —— 它本来就是独立的一列；
而时间先后**只能靠行序**表达。行序让给时间，信息量更大且一个字段都没少。

### 修复（四处，缺一不可）

**【1】新增 `_time_key(hm)`**（`core/salience.py`）
```python
def _time_key(hm):
    """把 'HH:MM' 转成可直接比大小的整数（分钟数）。解析不出返回 None。"""
    if not hm or not isinstance(hm, str):
        return None
    try:
        h, m = hm.strip().split(":")[:2]
        h, m = int(h), int(m)
    except (ValueError, AttributeError):
        return None
    if not (0 <= h <= 23 and 0 <= m <= 59):
        return None
    return h * 60 + m
```
- ★ 主键**不能用字符串比较**：`'9:35' > '10:00'` 在字典序下成立（`'9' > '1'`）
- ★ 主键**不能用画图那套「分钟序号」**（09:31=0 … 15:00=239，午休不占格）——
  那是为**横轴定位**设计的（午休若占格，图上会留两小时空白）；
  排序要真实钟点先后，`HH*60+MM` 跨午休天然单调（690 < 781）
- ★ 解析不出返回 `None`（**不是 0**，否则脏数据会挤到最前面）

**【2】三层排序键**
```python
def _key(r):
    tk = _time_key(r.get("time"))
    return (0, tk, r["idx"], -float(r.get("strength", 0) or 0)) \
        if tk is not None else \
        (1, 0, r["idx"], -float(r.get("strength", 0) or 0))
rows.sort(key=_key)
```
`(合法标志, 分钟数, 面板行序, 强度降序)` —— 不可解析的走 `(1, 0, …)` 排到队尾。

**【3】`timeline_summary` 新增 `topn` 参数 —— 这是最隐蔽的连带炸点**
```python
def timeline_summary(F, step=3, min_strength=1.5, topn=None):
    rows = [...]
    if topn is not None and topn >= 0:          # ① 先选：按强度取前 N
        rows.sort(key=lambda r: -float(r.get("strength", 0) or 0))
        rows = rows[:topn]
    rows.sort(key=_key)                          # ② 再摆：按时间升序
    return rows
```
> ★★ **改排序 = 改截断**。旧代码 `timeline_summary(F)[:24]` 依赖强度序才有
> 「取最强的 N 条」语义。改成时间序后，**同一行代码静默变成「取最早的 N 条」**：
> 尾盘整段消失、行数还是 24、不报错、不缺行 —— 最难发现的那类退化。
> 实测：误写 `[:18]` 时最晚只到 10:27，**丢掉 63 分钟**的尾盘节点。

同步修改：`report.py`（两份）的 `[:24]` → `topn=24`；
`salience.py` 的 `__main__` 打印 → `topn=18`。

**【4】界面文案 + 第四份副本（差点漏掉）**
- 表格 hint：`"按强度排序"` → `"按时间先后排列（早→晚）· 强度见末列"`
- **第四份副本是 JS 重写**：`templates/single_file_app.html` 的 `keyNodes()` 结尾同样是
  `.sort((a,b) => b.strength - a.strength).slice(0, limit)`。
  ★ 它是**另一种语言、另一个目录**，搜 `timeline_summary` 永远找不到它。
  → 教训：**修「某个函数」时要按语义找，不能按函数名找。**
  JS 侧同构修法：新增 `timeKey()` + `rowByTime()`，
  `keyNodes()` 拆成「先选（强度）→ 再摆（时间）」，
  且**归档路径也要重排**（旧归档按强度存的，不重排则历史回看仍乱）：
  ```javascript
  const fixed = ST.histRec.nodes.slice().sort(rowByTime);
  ```

## 九、十条铁律（踩过坑换来的）

1. **改排序 = 改截断**：任何按序输出的函数，改排序键前先搜所有 `[:N]` / `.slice(0,N)` 调用点。
2. **修"某个函数"要按语义找，不能按函数名找**：换语言的副本搜函数名永远找不到。
   本项目同一逻辑有 **4 份实现 / 6 个文件**（3 份 Python 副本 + 1 份 JS 重写）。
3. **数据层有序 ≠ 屏幕有序**：验证必须抵达屏幕（向 Qt 要字符串，别读像素）。
4. **空集合上的断言恒为真**：测试必须断言"至少产出了 N 条"。
5. **测试辅助函数不要重写生产逻辑**：复用生产函数，否则只验了"我的副本和我的副本一致"。
6. **源码级守卫必须用 `ast`**：文本级剥离（注释/docstring）永远有漏网之鱼。

# 接口使用风险说明（东方财富 / 腾讯财经）

> 本文是本仓库**最重要的一篇风险文档**。它不是免责套话，而是基于本项目开发期间
> **真实发生过的事件**整理出来的。
>
> 先给结论：**这个软件会直接请求公开行情接口，请求过密会被限流甚至封 IP，
> 而且一旦被封，本地不会自动恢复，只能等对方解封。**

## 二、风险是什么

### 2.1 三类可能发生的事

| 现象 | 表现 | 触发条件（观测到的） |
|---|---|---|
| **请求失败** | `RemoteDisconnected`、HTTP 4xx/5xx、返回空数组 | 请求频率偏高、并发突增 |
| **数据中断** | 面板只取到一部分板块就写盘 | 抓取过程中被限流 |
| **IP 被限制** | 该 IP 对该域名的**所有**接口都被拒（连 `baidu.com` 正常） | 持续高频访问后 |

### 2.2 关键认知：限流不是「均匀降速」，是「桶式放行」

观测到的通过率不是线性的。同一 IP 在受限期间：

- 可能连续被拒十几次，然后**突然放行几次**；
- 两个域名（`push2` / `push2delay`）的限流**彼此独立**，各自「服务一阵、拒绝一阵」；
- 拒绝往往在 **130~250 ms 内快速返回**（不是超时，是主动断开）。

这意味着：**「我请求少一点应该就没事」这个直觉并不完全成立** ——
即使低频也可能撞进拒绝窗口。只能降低概率，不能消除。

### 2.3 关键认知：被封之后本地不会自愈

被封期间：

- 全量抓取会失败或只拿到部分板块；
- 程序会回退到**本地面板**（上一交易日或当天已缓存的部分）；
- 如果当天从未成功抓取过完整面板，**这一天就没有数据**，且事后无法补
  （分钟接口只提供最近一个交易日）。

## 三、本项目开发期间的真实证据

> 以下数据来自项目自带的开发日志（`docs/archive-2026-09-21/更新日志.md`），
> 由作者在当时实测记录。本次归档**未复现**，仅如实转述。

### 3.1 通过率实测（2026-09-23）

| 时段 | 探测方式 | 结果 |
|---|---|---|
| 盘前 13:52~14:07 | 每 20 秒一个请求 | **45 次中放行 10 次（22%）** |
| 盘中 14:31 | 同上 | **2/10（20%）** |
| 收盘后 16:55 | 复测三个域名 | `push2` / `push2delay` / `push2his` **全部** `RemoteDisconnected`；同期 `baidu.com` 返回 200 |

**结论**：是目标站对该 IP 的限制，不是本地网络故障、不是代码缺陷。

### 3.2 数据被截断且不可恢复（2026-09-23 15:08）

该日一次全量抓取只取到 **122 个板块**（正常约 1000）就写盘。后果远不止「少几列」：

1. 抓取顺序是「行业在前、概念在后」，被截断的 122 个**几乎全是二/三级行业**；
2. `universe.clean_universe` 的行业层只保留 31 个**一级**行业 → 清洗后**只剩 5 个**；
3. 特征层 `F.codes == 5` → 辨识度榜 / 题材簇 / 主角更替 / 阶段对比**全部空掉**；
4. 界面上表现为「就绪 · 5 个板块」。

**且这份面板永久不可恢复** —— 东财的分钟接口只提供最近一个交易日，
09-23 之后无法再取到该日的分时数据。

### 3.3 更隐蔽的连锁反应

- **单点列把矩阵污染成 NaN**：956 列里有 834 列只有 1 个点。
  `salience.build_features` 的行中性化 `dV5 - dV5.mean(axis=1, keepdims=True)`
  只要该时刻**任意一列**是 NaN，整行均值就是 NaN → 顺着这一行污染**全部板块**。
  结果 `F.V` 只剩 1.0% 有限值 → 界面「大部分数据不显示」。
- **请求越多，封得越久**：日志中的复盘结论是「对已经封禁我们的服务持续猛打，
  只会让封禁更久」。这正是后来加入「升级式硬熔断」的直接原因 ——
  连续 5 轮熔断且零成功时，**连首次尝试都不发**。

### 3.4 作者踩过并记录的两个错误假设

| 假设 | 实测结果 |
|---|---|
| 「两个域名轮转能分摊负载」 | **反而慢 12×**：粘性优先 3.5 s / 150 板块，轮转版 42.8 s / 148 板块（295 次尝试、140 次失败、105 次冷却命中）。原因是两域名质量不对等，轮转把一半流量先推给了更差的那个 |
| 「`push2delay` 恒死」 | 13:51 全拒，13:58 完全正常（200 / 176 条 klines / 386 ms）。两个域名限流彼此独立 |

## 四、如何切换数据源

v3.0.6 起**默认是腾讯**（`source.DEFAULT_PROVIDER = TENCENT`）。
切回东方财富有三条入口，优先级从高到低：

| # | 方式 | 适用 |
|---|---|---|
| 1 | 环境变量 `FLOWLIVE_SOURCE=eastmoney` / `tencent` / `auto` | 脚本、快捷方式 |
| 2 | 数据目录下 `data/source.json` 写 `{"provider": "eastmoney"}` | 持久配置 |
| 3 | 界面按 **Ctrl+Shift+Alt+S** 显示「工具 → 数据源…（高级 · 暗门）」后选择 | 临时切换 |

**暗门只写日志、不做界面提示** —— 平时完全无感，需要时看日志就知道怎么切。

### 4.1 两个源的实测能力差异（务必知情）

| 能力 | 东方财富 | 腾讯 |
|---|---|---|
| 板块清单 | ✅ 约 1000（清洗后 400+ 概念 + 31 一级行业） | ✅ 31 行业 + 803 概念 + 31 地域 |
| 当前累计主力净流入 | ✅ | ✅（单位**万元**，需 ×10000 换算成元） |
| **分钟级资金流历史** | ✅ `fflow/kline` 240 点 | ❌ **没有** |
| 指数分钟分时 | ✅ | ✅（点位 + 成交量，非资金流） |
| 板块成分股 | ✅ | ❌ |
| 日级资金流历史 | ✅ | ❌ |
| 全市场个股快照 | ✅ | ❌ |
| 交易日历 | ✅ | ❌ |

**用腾讯时的如实标注**（源码中已实现，不是文档承诺）：

- 「东财全A」没有对应标的 → 用**中证全指 000985** 顶替，
  标签同步改为「中证全指（腾讯源替代东财全A）」；
- `fetch_sector_kline` 如实返回空并提示一次；
- 腾讯没有「领跌股」字段 → 该字段如实留空，不拿别的字段顶上；
- 状态栏显示 `源 tencent(替代)`。

### 4.2 腾讯源也有上限（实测）

`board_type=gn` 的响应体大小：

```
count=100  → 53,350 字节（正常）
count=200  → 106,205 字节（正常）
count=250  → 83 字节（服务端直接拒绝）
count=300  → 83 字节
count=500  → 83 字节
```

**上限恰好是 200**。源码里有 `RANK_MAX_COUNT = 200` 常量与
`clamp_rank_count()` 收敛，注释写明了「曾经调到 500 把整条降级通道打断」的教训。

> 教训：**提高数据源请求上限必须先实测**。单元测试不覆盖真实服务端行为 ——
> 那次是「改完立刻跑验收」才当场发现的，只跑单元测试会漏过去。

## 五、使用者应当怎么做

### 5.1 必做

1. **先读免责声明**（[DISCLAIMER.md](../DISCLAIMER.md)），确认你接受这些风险。
2. **在独立虚拟机里跑**（见 [README 第十节](../README.md#十虚拟机隔离运行建议)）。
3. **不要把刷新频率调到秒级**。默认 1 分钟已经能拿到「每分钟一个新值」
   —— 因为数据源本身就是分钟粒度，10 秒档和 60 秒档拿到的数据**完全一样**，
   区别只是「跨分钟后多久去取」。
4. **不要为了测试而压测**。想验证限流，用 `curl` 单发几次看响应，
   不要用本软件去撞。

### 5.2 建议

- 开一个独立浏览器/网络环境做对照，出问题时能区分「我这边网络」和「对方限制」。
- 记录异常时间点。日志里 `preflight ok`、`loaded ok`、`live-lite paint` 等行
  都带时间戳，出问题时这是唯一能区分「代码问题」和「限流」的证据。
- 如果发现某个域名开始频繁失败，**先停一会儿**，不要靠重试硬扛
  —— 源码里的硬熔断就是为这个设计的。

### 5.3 绝对不要做

- ❌ 用代理轮换、不断更换 IP、或任何方式**规避平台的访问限制**；
- ❌ 把本软件部署成对外的服务（多人共用会成倍放大请求量）；
- ❌ 把抓到的数据打包分发或商用（数据权利归数据提供方）；
- ❌ 在 Issue 里公开贴出可复现的高频请求脚本。
